# フェーズ5 手順書:取得・保存・表示の見直しと、お気に入り

- もとにした設計書:docs/02_design.md「6. 次に作るもの」の 6-1〜6-5(ログイン 6-6 と、ネット公開 6-7 は含まない)
- 順序(2026-10-12 承認済み):フロントエンドを仮の API で先に作り、バックエンドはあとから作って、最後に差し替える。
  - 理由:開いたときの流れ、お知らせ、スライドは、動かしてみないと使い心地が分からないため。先に形にして、サーバーが返すべきものをはっきりさせる。
- フェーズ3で作ったもののうち、作り直すもの:6時間ルールの判定、.env の取得間隔、取得の API の形(まとめて取得 → トピックを指定)。差分取得と保存の仕組みは、そのまま使う。
- 決まっていること:
  - さかのぼる範囲・件数の上限・保存する日数は、.env が空なら働かない(サンプルデータは投稿日が古く、絞ると何も取れない・すべて消えるため)。試すときだけ数字を入れる。
  - 件数の上限の数字は未決。仕組みだけを作り、数字は X API に切り替える前に決める。
  - 「新しい投稿があるか」は、取得の結果の件数ではなく、取得のあとの一覧の先頭が、今表示している先頭と違うかで判定する(開発中は React が処理を2回実行し、2回目の結果が0件になるため)。
- 用語:
  - 仮の API:画面の中だけで動く、本物と同じ名前・同じ形の関数。セクション12で本物に差し替える。
- フェーズ5の範囲外:ログイン、ネット公開、X API への切り替え。

- 作りについて決めたこと(セクション1〜3を作る中で決めた内容。続きのセクションも、これに合わせる):
  - 仮の API(client/src/api/dummyApi.js)は、本物の API 1・API 3 を呼んだうえで、新しい動きを画面の中だけでまねる。まだ取得していないトピックは、いちばん新しい HIDDEN_COUNT 件(3件)を隠し、refreshTopic を呼ぶと見えるようになる。覚えた内容は、再読み込みで元に戻る。失敗を試す切り替えは SHOULD_FAIL_REFRESH と SHOULD_FAIL_FAVORITE。
  - 関数の名前と返す形(本物も同じにする):fetchTopics() はトピックの配列、fetchPosts(topicId, offset) は { posts, has_more }(投稿に is_favorite が付く)、refreshTopic(topicId) は { topic_id, status, new_count }、setFavorite(postId, isFavorite) は { id, is_favorite }、fetchFavorites() は投稿の配列(投稿日時の新しい順)。
  - App の状態:一覧は list({ topicId, posts, hasMore })にまとめて持つ。request({ topicId, offset })が変わると保存済みの投稿を読み、refreshTarget({ topicId })が変わると、そのトピックを裏で取得する(取得 → トピックの一覧を受け取り直す → 最新の20件を読む)。取得を始めたトピックは refreshedTopicIds、失敗したトピックは failedTopicIds に記録する。
  - 新しい投稿の判定:取得のあとの最新の20件を freshPage に覚え、今の一覧にある投稿が出てくるまでを「新しい投稿」とする。最新の20件がすべて新しいときは、足すのではなく、一覧を入れ替える。
  - 位置合わせ:投稿の li に id="post-投稿のid" を付け、scrollTarget({ postId })が変わると、その投稿を画面の下のはしに合わせる(scrollIntoView の block は end)。
  - 更新ボタン(セクション4):refreshTarget に isManual(更新ボタンからなら true)を足し、自動の取得と同じ処理で取得する。更新ボタンからのときは、取得のあとの一覧を、お知らせをはさまずに足す。待ったあとの今の一覧は listRef(useRef)から読む。取得の最中は isRefreshing、「新しい投稿はありません」は noNewPostsNotice({ topicId })で持ち、3秒後に消す。
  - お気に入りのボタン(セクション5):App の handleToggleFavorite(postId, isFavorite) が setFavorite を呼び、返事のあとで list の中の is_favorite を書き換えて、成功なら true、失敗なら false を返す。送っている最中(isSaving)と失敗(isFavoriteError)は、カードごとの状態なので PostCard の中で持つ。
  - お気に入りのスライド(セクション6):App が favorites(お気に入りの投稿の配列)を持ち、開いたときに fetchFavorites で読む。付け外しが成功するたびに、fetchFavorites で読み直す(並び順はサーバーに任せる)。付け外しの処理は、一覧のカードとスライドのカードで、同じ handleToggleFavorite を使う。
  - サーバー側の案(セクション7〜11の着手時に、あらためて提案して決める):
    - .env の項目名:RETENTION_DAYS(保存する日数)、FETCH_RANGE_HOURS(さかのぼる範囲)、FETCH_MAX_COUNT(1回に取る件数の上限)。どれも空なら働かない。FETCH_INTERVAL_HOURS はやめる。
    - posts に足す項目:is_favorite(最初はすべて、お気に入りではない)。
    - API:POST /api/topics/:topicId/refresh(トピックを指定した取得)、PUT /api/posts/:postId/favorite(付ける・外す)、GET /api/favorites(お気に入りの一覧)。

## 2. 開いたときの流れの変更と、文言の変更  [x]
- 目的:サイトを開いたら、取得を待たずに、保存済みの投稿をすぐ表示する。

  - 投稿が0件のときの文言を「投稿がありません」に変える。
