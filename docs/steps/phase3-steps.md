# フェーズ3 手順書:取得の仕組み

- もとにした設計書:docs/03_phases.md「フェーズ3」
- 順序の変更:設計書の並び(fetcher → API 2 → 開いたときの流れ・ヘッダー → 入力チェック)を、フロントエンド先行に変更し、バックエンドは単独で確かめられる小さいもの(.env のチェック、API 3 の入力チェック)から始める(2026-10-10 承認済み)。
  - 理由:画面側の流れを仮の API 2 で先に固め、API 2 が返すべき形をはっきりさせるため。小さいものを先に済ませ、大きい API 2 に集中できるようにするため。
- 開いたときの流れ:設計書 4-3 の「API 1 → API 2 → API 3」に、API 2 のあとの API 1 の呼び直しを加え、「API 1 → API 2 → API 1 → API 3」とする(2026-10-10 ユーザー決定:ヘッダーの最終取得時刻を、取得後の値で表示するため)。設計書 4-3 と 03_phases.md に反映済み(2026-10-10)。
- 6時間ルール:制作中は6時間のまま進める(2026-10-10 ユーザー決定)。設計書の「使いながら見直す」は、完成後に実際に使ってから判断する。確かめるときは、6時間待つ代わりに、DB の最終取得時刻を古い時刻に書き換えて試す。
- 用語:
  - 仮の API 2:画面の中だけで動く、本物と同じ名前・同じ形の関数。サーバーには通信しない。
  - fetcher:投稿を取ってくる部品。取得元(sample / x)ごとに用意し、.env の FETCH_SOURCE で切り替える。フェーズ3では sample 用だけを作る。
- フェーズ3の範囲外:X API 用の fetcher(あとで追加)、レスポンシブ・起動方法・Tailscale(フェーズ4)。

# フロントエンド

## 1. 仮の API 2  [x]
- 目的:サーバーなしで、開いたときの流れ・取得失敗の表示を作れるよう、API 2 と同じ形の結果を返す関数を用意する。
- ファイルと置き場所:`client/src/api/dummyRefresh.js`(新規。関数名は `refreshPosts`。本物はセクション10で `refresh.js` に同じ名前で作る)
- 仕様(設計書 4-1、4-2):
  - 返す形:results(topic_id、status、new_count の一覧)。status は fetched / skipped / failed。
  - 「読み込み中」を確かめられるよう、返すまで少し待つ。
  - 取得失敗の表示を確かめられるよう、失敗させる切り替えを用意する。
- 確認:なし(次の確認はセクション3で、画面を組み立てたとき)

## 2. Header(サイト名と最終取得時刻)  [x]
- 目的:画面の上部に、サイト名と、選択中のトピックの最終取得時刻を表示する。
- ファイルと置き場所:`client/src/components/Header.jsx`(新規)、`client/src/components/Header.css`(新規)
- 仕様(設計書 1-3、1-5):サイト名と「最終取得: 月/日 時:分」(日本時間)。まだ一度も取得していないときの表示は着手時に提案する。
- 確認:なし(次の確認はセクション3で、画面を組み立てたとき)

## 3. App:開いたときの流れ・取得失敗の表示・ヘッダー  [x]
- 目的:サイトを開いたときに、タブの表示 → 取得 → 一覧の表示を順に行う。
- ファイルと置き場所:`client/src/App.jsx`(編集)、`client/src/index.css`(編集:取得失敗の案内の見た目を足し、使わなくなる .app-title を消す)
- 仕様(設計書 1-6、4-3):
  - 「取得に失敗しました」を出す場面:API 2 の呼び出しそのものが失敗したとき、または選択中のトピックの結果が failed のとき(設計書に、一部のトピックだけ失敗した場合の扱いがないため、着手時に決めた)。
  - 開いたとき:API 1 でタブを表示 → API 2 で取得(この間「読み込み中」)→ API 1 をもう一度呼んで最終取得時刻を受け取り直す → API 3 で選択中のタブの投稿を表示。
  - API 2 が失敗しても API 3 は実行し、「取得に失敗しました」と保存済みの投稿を表示する。
  - タブの切り替えと「もっと見る」では、API 3 だけを呼ぶ(今と同じ)。
  - ヘッダーに、選択中のトピックの最終取得時刻を表示する。
  - API 2 のあとに API 1 を呼び直す理由:最初の API 1 で受け取る最終取得時刻は、取得する前の値のため。API 2 のあとに受け取り直さないと、ヘッダーに1回分古い時刻が出る(2026-10-10 ユーザー決定:案A。API の形は変えない)。
- 確認:あり(Express を起動した状態で、開いたときの流れ・取得失敗の表示・ヘッダーが動く。API 1・API 3 はフェーズ2で本物になっているため、仮なのは API 2 だけ)

# バックエンド

## 4. .env の必須項目のチェック  [x]
- 目的:設定が足りないときに、サーバーを起動せず、足りない項目を表示する。
- ファイルと置き場所:`server/`(チェックの処理。ファイル名は着手時に決める)、`server/index.js`(編集)
- 仕様(設計書 3-6、5):DB接続情報(ホスト・ポート・ユーザー・パスワード・DB名)、取得元、取得間隔が必須。取得元が x のときは X APIキーも必須。スマホ用の待ち受けアドレスはフェーズ4。
- 確認:あり(.env の項目を1つ空にして起動すると、起動せずに足りない項目が表示される)

## 5. API 3 の入力チェック  [x]
- 目的:不正な topicId・offset に、正しいエラーを返す。
- ファイルと置き場所:`server/routes/posts.js`(編集)、`server/db/topics.js`(編集:トピックが存在するか調べる処理)
- 仕様(設計書 4-4、5):topicId は正の整数で、存在するトピック(形式違反は 400、存在しなければ 404)。offset は0以上の整数、省略時0(違反は 400)。エラーのときはステータスと error を返す。
- 確認:あり(ブラウザで不正なURLを開き、400 / 404 と error が返る)

## 6. topics の取得状況を読み書きする処理  [x]
- 目的:API 2 で使う、トピックの取得条件・最終取得時刻・最新の投稿IDを読み書きできるようにする。
- ファイルと置き場所:`server/db/topics.js`(編集)
- 仕様(設計書 2-2):取得条件(query_type、query_value)と取得状況(last_fetched_at、last_post_id)を読む。取得後に last_fetched_at と last_post_id を更新する。SQLは server/db/ の中だけに書く。
- 確認:なし(次の確認はセクション9で、API 2 を動かしたとき)

## 7. fetcher(sample 用)と取得元の切り替え  [x]
- 目的:投稿を取ってくる部品を作り、.env の設定で取得元を切り替えられる形にする。
- ファイルと置き場所:`server/fetcher/buildPosts.js`(新規:X API v2 形式の返事を投稿の形に組み立てる。入力チェックもここ)、`server/fetcher/sampleFetcher.js`(新規:sample 用の取得処理)、`server/fetcher/index.js`(新規:取得元の切り替え)
  - 追加分のサンプルは、ファイル名の末尾に `-added` を付けたもの(`oshi-posts-added.json`、`fanart-posts-added.json`)。ファイルがなければ、まだ投稿が増えていないものとして扱う。
  - 保存の処理を共通にする整理と、手動の取り込み(`importSample.js`)の扱いは、セクション9で提案する。
- 仕様(設計書 3-3、5):
  - 取得元は .env の FETCH_SOURCE(sample / x)で切り替える。x 用はあとで追加。
  - トピックと前回の最新投稿IDを受け取り、それより新しい投稿の一覧と、今回の最新投稿IDを返す。sample 用も x 用も同じ形で返す。
  - 投稿本体・ユーザー情報・画像情報を ID で突き合わせて、カード用の形に組み立てる。
  - 取得した投稿の入力チェック:投稿ID・投稿者名・@ID・本文・投稿日時・URLがそろっていること、画像は4枚まで。違反した投稿だけ保存せず、サーバーのログに記録する。
- 確認:あり(fetcher を単独で動かし、前回の最新投稿IDより新しい投稿だけが返る)

## 8. 追加分のサンプルデータ  [x]
- 目的:差分取得を確かめるため、「あとから増えた投稿」のサンプルを用意する。
- ファイルと置き場所:`server/sample/pending/oshi-posts-added.json`、`server/sample/pending/fanart-posts-added.json`(新規。データなのでコピー&貼り付けでよい)
  - pending は「まだ届いていない投稿」の置き場。fetcher は server/sample/ の直下だけを読むので、ここに置いている間は取得されない。セクション10で server/sample/ へ移動すると、新しい投稿が届いた状態になる。
- 仕様(設計書 3-4):X API v2 の形式。推しの投稿とファンアートの両方に、今の最新より新しい投稿を数件ずつ。
- 確認:なし(次の確認はセクション10で、サイトを開いたとき)

## 9. API 2(/api/refresh)  [x]
- 目的:サイトを開いたときに、新しい投稿を取りに行って保存するAPIを作る。
- ファイルと置き場所:`server/db/savePosts.js`(新規:取ってきた投稿を画像と一緒に保存する)、`server/routes/refresh.js`(新規:API 2 の入口)、`server/index.js`(編集:ルートを登録)
  - 手動の取り込み(`server/db/importSample.js` と `npm run import:sample`)は、API 2 と役割が重なるため、API 2 の確認後に削除する(着手時の提案。残す場合は fetcher と savePosts を使う形に書き直す)。
- 仕様(設計書 4-1、4-2):
  - POST /api/refresh。トピックごとに、last_fetched_at が空、または取得間隔(.env、6時間)以上前なら差分取得して保存し、last_fetched_at と last_post_id を更新する。そうでなければ skipped。
  - 返す形:results(topic_id、status、new_count)。1トピックの失敗は、ほかのトピックに影響させない。
- 確認:あり(API 2 を呼ぶと fetched になり、すぐ呼び直すと skipped になる)

## 10. 仮→本物:仮の API 2 を本物に差し替え  [x]
- 目的:画面の取得を、仮の API 2 から自分のサーバーの API 2 に切り替える。
- ファイルと置き場所:`client/src/api/`(新規:API 2 を呼ぶ処理)、`client/src/App.jsx`(編集:読み込み先の差し替え)、仮の API 2 のファイル(削除)
- 仕様:仮→本物。関数の名前と返す形は仮の API 2 と同じなので、App は読み込み先を変えるだけにする。
- 確認:あり(フェーズ3の完了条件)
  - サイトを開くと、追加分のサンプル投稿だけが新しく表示される。
  - 6時間以内に開き直しても取得されない(skipped)。
  - 不正な topicId・offset でエラーが返る。
